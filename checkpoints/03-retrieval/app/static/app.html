    How routing works

    What the routed strategy does before it searches: a model writes a plan, code checks it, SQL runs it. The grey chips are where it lives in the code. app/rag/router_llm.py · app/rag/router.py · app/rag/retriever.py

    The idea in one minute

    Top-k is a budget. "Who works in the San Francisco office?" has six right answers, one per row of the team directory. Top-5 search can return at most five of them, however good the embedding. No reranker fixes that: the answer is bigger than k. So before searching, the router decides what shape the question has.

    pointwise

    "I'm locked out of my laptop. Who do I ring?"

    The answer is in one or two passages.

    → normal hybrid search + rerank

    aggregation

    "Who works remotely?"

    The answer is a set of rows matching a value.

    → SQL lookup, every match, no k

    aggregation_unindexed

    "Who speaks Spanish?"

    A list, but by something no record set stores.

    → normal search + log the gap

    The routes are the constants in app/rag/router_llm.py:48-51. The model only picks from a menu. It never writes the query that runs.

    Say this"The model picks from a menu built from our data, code checks every pick, and SQL does the lookup. If the model is down, the old regex rules take over: the search gets worse, it never fails."

    One question, step by step

    1. 0

      At sync time: every CSV row keeps its columns once, not per question

      The parser turns each row of team-directory.csv into one chunk and keeps its columns. The sync stores them as JSON on that chunk: {"office": "Remote", "department": "Engineering", ...}. Because the fields sit on the chunk itself, they get the same tenant, access, status and date protection for free.

      app/ingest/parsers.py:141app/ingest/sync.py:260app/db/migrations/007_record_fields.sql

    2. 1

      Build the menu from the data

      One SQL query lists every record set this user may read, with each column and every distinct value in it. ROUTABLE then trims it to the columns we allow as filters (office, department, role, but not name or email: those point at one person, which makes the question pointwise). No readable record set means no menu, so the question goes straight to search with no model call.

      PEOPLE-DIRECTORY: the team directory, one row per person (12 rows)
    department: Design, Engineering, Human Resources, Product
    office: New York, Remote, San Francisco
    role: Data Scientist, DevOps Engineer, ...

    3. 2

      Ask the model for a plan (JSON, not prose)

      The menu is pasted into the prompt where it says {{VOCABULARY}}. The model maps synonyms ("NYC" → New York, "work from home" → Remote) and replies with one JSON object. A reply that isn't JSON gets one retry, with the bad reply quoted back.

      {"route": "AGGREGATION", "source": "PEOPLE-DIRECTORY",
 "filters": {"office": ["Remote"]}, "missing_column": null,
 "reasoning": "Every person whose office is Remote."}

    4. 3

      Code checks every field of the plan

      Nothing the model wrote is trusted until it matches the stored rows. Either every filter checks out or no list runs at all, because quietly dropping a bad filter would widen the list ("Remote AND Wizard" would become "Remote"). The checks are in the table below.

      app/rag/router_llm.py:161

    5. 4

      Run the route

      aggregation: the code builds the SQL itself, with the checked values passed as parameters (fields->>'office' = ANY(...)), inside the user's access filter. It returns every match. No filter returns nothing, never "everything".
      pointwise / unindexed: the usual hybrid search + rerank, exactly like hybrid_rerank.

    6. 5

      Write down what we couldn't list

      Every aggregation_unindexed question is appended to runs/router_misses.jsonl. The most-asked missing column is the next one worth adding. A full disk never fails the search.

    Adding a record set is one entry

    The menu, the prompt, the checks and the lookup all read ROUTABLE and the stored fields. Nothing else about a record set is written by hand. The tickets are the second entry: listable by reporter, and by a status from a fixed list. The menu offers exactly that list, and the sync reports any row whose status isn't on it. (The regex fallback still only knows the directory.)

    Evals

    How good is each search technique, in four numbers. This page only reads what the scripts saved in runs/: run them in a terminal, then Refresh. Admins only, because a run names the documents every persona got back. GET /evals/scoreboard · /evals/routes · /evals/answers

    The idea in one minute

    We built ten ways to search. To know which one works, we grade them like an exam: an answer key written first (for every question, the document and the words the answer needs), then four numbers. Two grade the search, two grade the answer. The names are RAGAS's, the standard library for RAG evals.

    Search did it bring the right material?

    Context recallDid everything the answer needs arrive?
    Context precisionWas it near the top?
    →

    Answer did the model use it well?

    FaithfulnessDoes it stick to what it was given?
    Answer correctnessIs it actually right?

    Three of the four come straight from the answer key, no model needed. Faithfulness needs an LLM judge. The key is never edited to suit a technique: if a technique misses a question, fix the technique.

    Say this"Two numbers for the search, two for the answer. When an answer is wrong, they tell us whose fault it is: search never brought the facts, or the model had them and still got it wrong."
