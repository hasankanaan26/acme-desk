How the sync spots a change: eTag, content hash, labels

Three fingerprints per document, checked cheapest first. Only a changed content hash costs embedding money.

SignalWhat it isCost to checkChanges when
eTag A fingerprint of the file's bytes. The source hands it out with every listing: Drive calls it md5Checksum (a version number for native Docs), SharePoint calls it an eTag. The local folder computes the same MD5, so identical bytes get identical eTags. Free: comes with the listing, no download Any byte changes: an edit, a new footer, even a re-save
Content hash SHA-256 of the chunks we would store, after parsing, PII redaction and chunking, plus the pipeline and parser versions. Download and parse the file The text we would embed changes. Same hash = same vectors.
Labels The register fields copied onto every chunk: who may read it, status, version, dates. Free: read from the register Someone changes permissions, status or dates in the register

The decision, top to bottom: the first "yes" wins

  1. Draft, withdrawn, or no register entry? → skip (remove if it was indexed)
  2. Same eTag as the index? → unchanged, not even downloaded. If only the labels differ: relabel
  3. Downloaded, but no text (a scan)? → quarantine
  4. Not in the index yet? → add: embed
  5. Content hash differs? → change: embed the new chunks, then delete the old ones
  6. Labels differ? → relabel: update the metadata, no embedding
  7. Only the bytes differ? → touch: store the new eTag, no embedding
  8. In the index, but gone from the source? → remove
